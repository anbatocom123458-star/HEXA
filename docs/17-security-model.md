# Security model

HEXA's security model is **honest by design**. It makes strong, *specific*
guarantees and does not pretend to make impossible ones. This page is the
single most important thing to read before trusting HEXA with real data.

## What HEXA protects

### Compile-time secret containment

The core guarantee: **a secret never silently becomes ordinary data.** The
compiler enforces this as a build failure, not a warning.

- A security-sensitive value (`secret`, `key`, `private_key`, `apikey`,
  `password`, `credential`) **cannot be printed** (`print(x)` → `E2100`).
- It **cannot be cast** to ordinary `text`/`bytes` (`E2102`).
- It **cannot be used** where ordinary data is required (`E2101`).
- The only sanctioned path outward is the deliberate, explicit
  `secret.export(...)`.

This stops entire classes of accidental leaks: passwords dumped to logs, keys
echoed to the terminal, private keys serialized into files — all become
compile errors.

### Authenticated encryption

- Encrypted data is both confidential *and* tamper-evident. A corrupted or
  wrongly-keyed ciphertext is rejected. It is never silently mis-decrypted.

### One-time key integrity

- Encryption keys generated by `hexa encrypt` are displayed exactly once, then
  destroyed. There is **no** `key show` / `recover` / `reveal`; the
  `key show` command always fails with `EKEY-004`. This means a compromised
  machine that steals your *files* cannot also steal your *keys* from HEXA,
  because HEXA never stored them.

### Good cryptographic hygiene by default

- Memory-hard KDFs for passwords (Argon2id preferred), HKDF key hierarchies for
  multi-layer encryption, fresh random salts and nonces, modern authenticated
  ciphers, and a versioned container format that detects format drift.

## What HEXA does NOT protect (honestly)

These are outside the scope of any tool, and HEXA says so plainly:

- **A compromised operating system.** If malware or a rootkit is running on
  your machine, it can read process memory, intercept syscalls, and log
  keystrokes. HEXA cannot defend against an attacker who already owns the OS.
- **Malware & keyloggers.** Software on the machine can observe input and
  output, including `secret.export` results.
- **Reverse engineering.** Native binaries can be disassembled and analyzed
  (HEXA itself ships a `disassemble` command). Security comes from protecting
  keys and values, not from hiding code.
- **One-time key loss.** If you lose the displayed `HX-<hex>` key, the data is
  unrecoverable. That is the trade-off for never storing it.
- **Absolute brute-force impossibility.** No cipher makes brute force
  "impossible"; strong keys make it *infeasible*. HEXA never claims
  "uncrackable."
- **Terminal scrollback & screenshots.** Anything shown via `secret.export` (or
  the one-time key display) is ordinary text in your terminal from then on and
  can be captured.
- **Side channels.** Power/EM/timing side-channel resistance is not claimed for
  this milestone.

## The threat model in short

HEXA's job is: **keep secrets out of the hands of your own programs and your
own mistakes.** Its job is *not*: **keep secrets out of the hands of an
attacker who already controls your machine.**

For a detailed treatment — adversary profiles, trust boundaries, residual
risks, and mitigations — see the dedicated
[Threat model](27-threat-model.md).

## Practices that keep you safe

- Store the one-time key somewhere safe (an offline password manager) the
  instant it appears.
- Run on a machine you trust, with an up-to-date OS and no unknown malware.
- Wipe secrets when done (`secret.wipe`).
- Prefer `secret.input` over `input.text` for anything sensitive.
- Do not copy secrets into scrollback/screenshots.
- Use strong, unique passwords and memory-hard KDFs.
